# 计划书：本地合成证明（暂名）

> HacKU 2026 · FinTech 第 1 题「Give a Machine a Wallet – Agentic Commerce」（HKT 赞助）
> 队伍 23「Local deployment」
> 本文只讲点子、题目契合度与创新点，不含开发计划。

---

## 一句话

**代理替你付款时，每一方只在自己的数据上回答一个固定的是非题并签名；你的手机按公开公式把这些结论合成分数，银行自己重算一遍。个人背景不出手机，只出签过名的结论。**

路演版：**过去的支付用隐私换安全；我们让安全在本地被证明，隐私留在原地。**

---

## 1. 要解决的问题

### 1.1 代理一出现，旧风控信号就失灵

今天的网购风控默认「人在结账」：IP 在哪，人就在哪；设备就是你的手机；半夜三点下单本身就可疑。

代理下单时，这三条全错：请求来自云服务器，设备是服务器，代理本来就会在你睡觉时下单。银行只剩两种选择：

- 把代理订单都当可疑来拦，用户被问到烦，代理形同虚设；
- 不看这些信号，骗子和提示注入就有空子钻。

### 1.2 要安全，就得交隐私

为了判断「是不是本人」，现有的风控把资料集中上传。EMV 3-D Secure 2 一次验证可以带上上百项设备、浏览器、地址资料给发卡行；第三方风控公司还会跨商户拼出你的行为画像。资料越集中，泄露和被追踪的风险越大。

### 1.3 代理自己就是泄露口

如果代理手里有你的位置、历史和习惯，它被网页里藏的指令劫持时，这些资料也能被带走。2026 年业界的共识是：提示注入在模型层面挡不住，只能限制代理能接触什么、能动多少钱。

### 1.4 我们选定的用户和消费决定

题目要求「选一个消费决定，以及一个委托它的人」：

- **委托人**：在香港读大学的 Gen Z 学生。
- **消费决定**：让购物代理在香港网店买 HK$800 以内的电子配件，寄到宿舍或家里。
- **为什么选它**：
  - 有收货地址，位置比对才有意义；
  - 第一次光顾的网店很常见；
  - 网购诈骗针对的正是这类交易；
  - 付款方式正好覆盖题目点名的卡（Mastercard、UnionPay）和转数快。

## 2. 点子本身

### 2.1 四个角色

| 角色 | 是谁 | 知道什么 | 不知道什么 |
|---|---|---|---|
| 代理 | 云端的购物代理 | 要买什么、哪家店、多少钱 | 你的位置、消费历史、生物特征 |
| 发证方 | 定位服务（手机系统或地图）、银行、商户 | 各自只有自己那份数据 | 其他两方的数据 |
| 合成方 | 你的手机 | 收到的签名结论 | 不需要看三方的原始数据 |
| 验证方 | 发卡行或付款银行 | 签名结论、合成分数、订单 | 你的坐标、你在别家买过什么 |

### 2.2 每一方只回答一个固定的是非题

| 发证方 | 固定问题 | 看自己的什么数据 | 交出去的 | 留在原地的 |
|---|---|---|---|---|
| 定位服务 | 最近 3 小时内，本人是否在收货地 5 公里内？ | 手机的定位记录 | 「是 / 否」+ 签名 | 坐标、行踪 |
| 银行 | 本人是否刚用指纹或人脸批准了这一单？ | 通行密钥的签名（比对在手机上完成） | 「已批准」+ 签名 | 生物特征（银行本来也拿不到） |
| 商户 | 这一单和本人过去的购买习惯是否一致？ | 自己店里的订单记录 | 「一致 / 不一致」+ 签名 | 购买明细 |

每一份结论都写明：这一单的编号（订单内容的哈希）、发证方、问题编号、回答、签发时间、过期时间，再加发证方的签名。

### 2.3 分数不是让人相信的，是让人重算的

加分表是公开的。手机把所有结论和合成出的分数一起交出去。验证方逐项验签、核对订单编号和时效，再用同一张表自己重算一遍：对得上才接受。用户改不了任何一份结论，因为结论不是他签的。

### 2.4 七条设计原则

1. **验人，不验请求。** 把「代理的请求从哪来」和「代理背后的人此刻在哪、交代过什么」分开。旧风控把两者混在一起，代理时代就失灵。
2. **数据不集中，只交结论。** 三方资料从不在任何一台服务器上汇合。
3. **分数可重算。** 验证方不信任分数，只信任签名，自己算。
4. **只紧不松。** 本地结论最多只能让交易走得更严（要求确认、冷静期、否决），永远不能突破授权书和银行设的上限。伪造一个「很安全」，也什么都多拿不到。
5. **缺一份，按最差算。** 必交哪几份由规则规定，不能只挑对自己有利的结论交。这条也让推广不靠「大家先一起加入」：只有一方参与也能用，缺的按更严的路径走。
6. **问题和阈值是固定的。** 不能用「1 公里内？2 公里内？3 公里内？」一圈圈逼出你的位置；每一单每个问题只问一次。
7. **平时私密，纠纷时可举证。** 手机把当时比对用的资料做成哈希，签进结论、写进日志，原始资料留在本地。发生纠纷时，用户可以选择交出原始资料，任何人都能对上那个哈希。

### 2.5 和我们已有的规则引擎的关系

原有的规则引擎（16 条规则、四条通道、一次性凭证、哈希链日志）就是执行层：合成分数决定这一单走「直接过、问一次、冷静期、拒绝」哪一条，单笔上限、7 天上限、商户锁定照样由引擎执行。引擎的不变量本来就是「不调用模型、不读外部状态、所有输入通过参数传入」，所以它能直接在手机端运行。

## 3. 与题目的契合度

### 3.1 题目的范围要求

| 题目原文要求 | 我们怎么满足 |
|---|---|
| 选一个消费决定和一个委托人 | 大学生委托代理在香港网店买 HK$800 以内的电子配件（见 1.4） |
| 定义代理能做什么、不能做什么 | 代理能搜索、加购、提交付款方案；不能付款，也拿不到任何个人背景 |
| 限额如何真正执行（上限、授权书、过期、规则、撤销） | 规则引擎执行上限、授权书和过期；发证方拒签等于撤销；本地结论只紧不松 |
| 端到端演示一笔完整交易 | 代理下单 → 三方签结论 → 手机合成 → 银行重算 → 规则引擎放行 → 一次性凭证结算 |
| 至少一次代理被拦下 | 见 3.3，至少五种拦截 |
| 付款路径与积分可以是重点 | 我们的重点放在付款路径的验证上；积分不是主线 |

### 3.2 题目要求的证据

| 题目原文要求 | 我们的证据 |
|---|---|
| 先展示代理被允许做什么的日志，再展示它被拦下 | 哈希链日志：开头记授权书内容，之后每一单记三方结论、分数、通道 |
| 和人工流程对比：步骤、时间、花费 | 对比今天网购结账：要填几项、交出几项个人资料、拿学生优惠要上传什么。由队伍在真实网店实测并截图 |
| 讲明代理按哪条规则决定 | 公开的加分表 + 规则编号；每次拦截都能指出是哪一份结论、哪一条规则 |
| 所有费率、费用、积分都要亲自观察并打时间戳 | 机制本身不依赖任何费率；若引用费率或 3D Secure 数据项数，一律附截图或规格出处 |

### 3.3 被拦下的情形

| 情形 | 谁拦下 |
|---|---|
| 代理被劫持，把收货地改到外地 | 定位结论变成「否」，要求本人确认 |
| 拿上一单的结论来重放 | 订单编号对不上，验签失败 |
| 只交对自己有利的结论 | 缺失按最差算，被拦 |
| 直接改分数 | 银行重算对不上，拒绝 |
| 金额超出授权书上限 | 规则引擎拒绝，不论分数多高 |

### 3.4 题目「可选方向」里我们正面回应的几条

- **一份第三方不必信任运营者也能核对的日志**：结论由三方各自签名，分数可重算。
- **用记录下来的规则回答「它为什么这样做」**，而不是事后补写解释。
- **一份商户愿意接受的记录，和一家不接受的商户**：商户可以选择是否签发结论；不签，就按缺失处理。
- **认出访客是代理、就区别定价的商家**：代理拿不到个人背景，商家也就无从按人定价。
- **升级给人之后没有回应、请求过期**：结论有过期时间，过期即缺失。

## 4. 创新点

| # | 创新点 | 现有做法 | 我们的不同 |
|---|---|---|---|
| 1 | 验人不验请求 | 风控看请求的 IP、设备、时间；代理时代这些信号失灵 | 把代理的请求和背后的人分开验；只拿人的背景来比对这一单 |
| 2 | 多方各自回答，本地合成 | 资料集中上传到发卡行或风控公司 | 三方资料从不汇合；只交签名的是非结论 |
| 3 | 分数可重算 | 风控分数是黑盒，用户和商户都看不懂 | 公开加分表，验证方用签名结论自己重算 |
| 4 | 只紧不松 | 风控分数既能放行也能拦截，被伪造就失守 | 本地结论只能让交易更严，突破不了授权上限 |
| 5 | 缺失按最差算 | 一般系统缺资料就报错，或者干脆跳过 | 既防止挑着交结论，也让推广不必等所有方同时加入 |
| 6 | 固定问题防拼凑 | 精确位置或可调阈值会一点点泄露隐私 | 问题和阈值写死在公开规则里，每单只问一次 |
| 7 | 平时私密，纠纷可举证 | 要么全交资料，要么事后无凭无据 | 签名里放资料的哈希，原始资料留在本地，需要时才交出 |
| 8 | 代理是瞎的 | 代理拿着用户资料去购物 | 代理拿不到任何个人背景，被注入也泄露不了 |

**我们不声称的事：** 这不是新的密码学，也不是零知识证明。用到的签名、哈希、通行密钥、可验证凭证格式都是现成的、经过验证的积木。新的是组合方式，以及把它放在代理付款前的最后一关。

## 5. 竞品与相近技术

### 5.1 最接近的参照：Apple Private Access Tokens

Apple 在 iOS 16 和 macOS Ventura 加入了 Private Access Tokens，基于 IETF 的 Privacy Pass 标准，最早和 Cloudflare、Fastly 合作。手机向网站证明「我是真设备、背后是真人」，网站就跳过图片验证码，但拿不到你是谁。

**我们的定位：把这个思路从「跳过验证码」扩展到「付款」，从一个发证方（Apple）变成多个（定位、银行、商户），并且证明的不只是「人在」，还有「这一单符合这个人此刻的情况」。**

### 5.2 对照表

| 方案 | 它证明什么 | 交出去什么 | 它不做什么 | 和我们的关系 |
|---|---|---|---|---|
| Apple Private Access Tokens / IETF Privacy Pass | 是真设备、真人 | 一个匿名令牌 | 不涉及付款，不看这一单的内容 | 最接近的参照；我们是它的付款版、多发证方版 |
| EMV 3-D Secure 2 | 持卡人是不是本人 | 上百项设备、浏览器、地址资料 | 不保护隐私；代理从云端下单时信号失灵 | 反方向：我们不上传资料，只交结论 |
| W3C Secure Payment Confirmation | 用户用生物认证确认了这个收款方和金额 | 一份签名 | 只有银行一方，不比对位置和习惯 | 我们的银行结论可以直接用它 |
| Apple Pay / 卡组织网络代币 | 卡在这台设备上，用户用 Face ID 批准了 | 设备代币 + 签名 | 不判断这一单是否符合用户此刻的情况 | 互补：它管卡，我们管「这一单该不该」 |
| Stripe 一次性付款凭证（ACP） | 这张凭证只能用在这家店、这个金额 | 一次性凭证 | 不判断是不是本人、本人在不在场 | 互补：结算层用它 |
| Visa Intelligent Commerce / Trusted Agent Protocol | 代理身份可信，凭证有上限 | 代理专用代币 + 消息签名 | 不使用用户此刻的背景 | 互补：它验代理，我们验人 |
| Mastercard Agent Pay / Verifiable Intent | 代理代币绑定了同意的策略；交易背后有用户的意图 | 代理代币 + 意图证明 | 意图证明在 Mastercard 自己的体系里；不比对位置和习惯 | 最接近的卡组织方案；我们的结论可以作为它的额外证据 |
| Google AP2 | 用户签过意图、购物车、付款三段授权 | 签名的授权书 | 不判断签名时是不是本人、本人在不在场 | 互补：AP2 证明「授权过」，我们证明「此刻是本人、情况相符」 |
| Web Bot Auth（IETF 草案） | 这个请求来自某家公司登记过的代理 | 请求签名 | 只验代理，不验背后的人 | 互补 |
| W3C 可验证凭证 / OpenID4VP / SD-JWT | 一份凭证由谁签发、只出示其中几项 | 选定的声明 | 本身只是格式，不规定怎么判断风险 | 我们签名结论的格式基础 |

### 5.3 我们填的空位

业界已经把「代理拿不到卡号」（一次性凭证、代理代币）、「代理身份可信」（Web Bot Auth、Visa）、「用户授权过」（AP2、Mastercard Verifiable Intent）都做了。还空着的是：**付款这一刻，怎么证明代理背后的人在场、情况相符，又不把这个人的资料交出去。** 我们就填这个位置。

## 6. 支付通道接入可行性

题目评分只看提出的支付通道是否现实。以下是提案，不是已经接通的集成：

- **Mastercard**：验证方放在发卡行。签名结论随卡交易的验证资料一起送到发卡行，作为 Agent Pay 和 Verifiable Intent 之外的额外证据。
- **UnionPay**：同样由发卡行作为验证方，在授权前读取结论并重算分数。
- **转数快**：转数快是付款人在自己的银行 App 里发起的推送式付款，即时到账，付出去一般追不回，所以付款前的把关更重要。验证方就是付款人的银行 App，最容易落地。
- **需要谁持牌**：发证和验证都在持牌银行或现有的定位服务方。我们提供的是规则、结论格式和合成方法，不碰资金。

## 7. 边界与风险

- **手机被控制，定位结论也能造假**（例如假定位软件）。手机硬件的设备证明能挡住一部分，挡不住的由授权上限兜底：最多亏用户事先设的那个数。
- **商户自证有利益冲突。** 商户想成交，倾向回答「一致」。所以商户结论的权重压低，或者只问对它没有好处的问题。
- **订单本身一定要出去。** 商户、金额、商品，以及实体商品的收货地址，都必须交给商户。能留在手机上的，是位置、消费历史、习惯和原始意图这些个人背景。
- **推广需要发证方配合。** 我们的回答是「一方也能用」：只有手机自己的定位加通行密钥也能工作，多一方，分数更准。
- **加分表的权重是人设的**，不是从真实诈骗数据训练出来的；效果要用回放场景实测，拦截率和误拦率都要自己跑出来，不编数字。
- **演示里的三个发证方是模拟的**，只有通行密钥是真的；路演要主动讲明。
- **清醒地被骗时挡不住。** 用户本人在场、情况相符、自己确认了，系统就会放行。我们保证的是上限，而不是零损失。

## 8. 说法守则

| 不要说 | 要说 |
|---|---|
| 去中心化 | 数据分散、本地合成 |
| 零知识证明 | 签名的是非结论、最小披露 |
| 所有数据不上传 | 个人背景不出手机，只出签过名的结论 |
| 误杀归零、赖不掉账 | 给银行多了一类以前拿不到、又不侵犯隐私的证据 |
| 比通行密钥更安全 | 比把卡号和个人资料交给代理、商户更安全、更私密 |
| 没有人让代理独立付款 | Stripe、Visa、Mastercard 已让代理付款；没人解决的是付款时怎么证明人在场又不交资料 |

## 10. 评审当天让在线演示保持醒着（给队友）

在线演示放在 Render 免费版上。15 分钟没人访问，网站就会休眠，下一个人打开要等大约一分钟。评委第一次打开时如果一直在转，很可能以为网站坏了。

办法：用一个免费的定时访问服务，每 10 分钟自动访问一次网站，让它一直醒着。

**谁来做：** 任何一个队友，用自己的邮箱注册，大约 5 分钟。

**什么时候开：** 交件前（12:00 左右）打开，一直开到颁奖结束（18:50）。FinTech 展览是 13:30–14:30，决赛路演是 16:20–17:40。

**步骤（cron-job.org）：**

1. 打开 https://cron-job.org ，免费注册并登录。
2. 点 **Create cronjob**。
3. Title 填 `HacKU demo keep-awake`，URL 填 `https://hacku-local-deployment.onrender.com/api/config`。
4. 执行时间选每 10 分钟一次（Every 10 minutes）。
5. 保存。几分钟后，在这条任务的历史记录里应该看到状态码 200。
6. 比赛结束后，把这条任务停用或删除。

**为什么访问 `/api/config`：** 这个地址只返回服务器配好了哪些功能，例如 `{"llm_available":true,"search_live":true,...}`。它不会启动代理，也不花任何 API 费用。

**怎么确认有效：** 隔 20 分钟以上，用手机打开网站，几秒内就应该出来，而不是转一分钟。

**备用：** UptimeRobot（https://uptimerobot.com ）免费版也能做：新建一个 HTTP 监控，间隔 5 分钟，地址同上。

**展台上：** 现场网络不稳时，在电脑上运行 `npm start`，打开 http://localhost:8787 演示，功能一样。
